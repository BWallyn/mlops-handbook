### Q1 — Branch origin

You are about to build a new feature: a FastAPI serving endpoint. Which command sequence is correct?

**A.**
```bash
git checkout main
git checkout -b feature/fastapi-serving-endpoint
```

**B.**
```bash
git checkout develop
git pull origin develop
git checkout -b feature/fastapi-serving-endpoint
```

**C.**
```bash
git checkout develop
git checkout -b feature/fastapi-serving-endpoint
```

**D.**
```bash
git checkout -b feature/fastapi-serving-endpoint
```

<details>
<summary>Answer</summary>

**B.**

You must always branch from `develop`, and you must always `pull` before branching. Option C skips the pull — if `develop` has moved since your last fetch, your branch starts from a stale point and will have a larger, messier merge conflict later. Option A branches from `main`, which is wrong: `main` only ever receives merges from `release/*` and `hotfix/*`. Option D branches from wherever `HEAD` currently points, which is unpredictable.

</details>

### Q2 — Commit message audit

A teammate submits these four commits in a PR. One is acceptable, three are not. Identify the acceptable one and explain what is wrong with each of the others.

```
a) "stuff"
b) "feat: add drift detection"
c) "feat(monitoring): add Evidently DataDriftPreset report to monitoring pipeline"
d) "Fixed the bug with the NaN values in the prediction endpoint that was causing 500 errors in production"
```

<details>
<summary>Answer</summary>

**Acceptable: c.**

- **a** — No type prefix, no description, tells you nothing about what changed or why.
- **b** — Has a type prefix, but the scope is missing and the summary is too vague. "Add drift detection" to what? Where? How?
- **c** ✓ — Follows Conventional Commits: type (`feat`), scope (`monitoring`), and a specific imperative-mood summary that names the exact tool and location.
- **d** — The content is actually good (specific, explains the why), but the format is wrong: no type prefix, past tense instead of imperative mood, and it is far too long for a summary line. The detail belongs in the commit body, not the first line. The first line should be something like: `fix(serving): guard against NaN input in prediction endpoint`.

</details>

### Q3 — Merge direction

Your `hotfix/fix-model-version-mismatch` branch is ready. Into which branches must you merge it, and in which order?

<details>
<summary>Answer</summary>

**First into `main`, then into `develop`.**

The sequence matters: you merge into `main` first because that is the production fix. You then tag `main` with the new patch version. Then you back-merge into `develop` so the fix is not lost when the next release is cut from `develop`. If you merge into `develop` first and something goes wrong with the `main` merge, you have a polluted `develop` with no corresponding production release.

Never merge a hotfix only into `main` and forget `develop` — that is the most common Git Flow mistake and it guarantees you will re-introduce the bug in the next release.

</details>

### Q5 — Fast-forward vs. no-fast-forward

Explain what happens differently between these two commands, and which one Git Flow requires.

```bash
# Option A
git checkout develop
git merge feature/add-experiment-tracking

# Option B
git checkout develop
git merge --no-ff feature/add-experiment-tracking
```

<details>
<summary>Answer</summary>

**Option A (fast-forward, the default):** If `develop` has not moved since you branched, Git simply moves the `develop` pointer forward to the tip of `feature/add-experiment-tracking`. No merge commit is created. The history looks completely linear — you cannot tell that the work happened on a separate branch.

**Option B (`--no-ff`):** Git always creates a merge commit, even if a fast-forward is possible. The history retains the branching structure: you can see exactly which commits belonged to `feature/add-experiment-tracking` and when it was integrated.

**Git Flow requires `--no-ff`** for all merges into `develop` and `main`. In a production ML system, being able to identify "which commits were part of the experiment-tracking feature" is essential for debugging, auditing, and reverting a whole feature atomically (`git revert -m 1 <merge-commit-hash>`).

In GitHub, this corresponds to disabling "Allow squash merging" and "Allow rebase merging" in repository settings, leaving only "Create a merge commit" enabled.

</details>

### Q7 — Undoing a mistake

You have just run `git reset --hard HEAD~2` on `develop` and force-pushed. Two minutes later, a teammate messages you saying their local `develop` is now broken. Explain what happened and what you should do now.

<details>
<summary>Answer</summary>

`git reset --hard HEAD~2` rewrote history by erasing the last two commits from `develop`. When you force-pushed, the remote `develop` no longer contained those commits. Your teammate's local `develop` still points to one of the erased commits, which no longer exists on the remote — their branch has "diverged" from a history that has been deleted.

**What to do:**

1. Immediately coordinate with the team. No one should push to `develop` while you are recovering.
2. Recover the lost commits using `git reflog` (the reflog records every HEAD movement, including the reset):
   ```bash
   git reflog
   # Find the commit hash before the reset, e.g. a3f8c12
   git checkout -b recovery/develop-fix a3f8c12
   ```
3. Reset `develop` back to the recovered state and force-push again:
   ```bash
   git checkout develop
   git reset --hard a3f8c12
   git push --force-with-lease origin develop
   ```
4. Ask every affected teammate to run:
   ```bash
   git fetch origin
   git reset --hard origin/develop
   ```

**The lesson:** `git reset --hard` on a shared branch is always wrong. The correct tool is `git revert`, which creates a new commit that undoes the change without touching history. Reserve `--hard` reset and force-push for your own local, unshared branches only.

</details>

### Q8 — Release branch rules

You have just cut `release/2.0.0` from `develop`. A teammate opens a PR against `release/2.0.0` that adds a brand-new feature: support for async batch inference. Should you merge it? Why?

<details>
<summary>Answer</summary>

**No.** Once a release branch is cut, it is frozen for new features. Only bug fixes, version bumps, and last-minute documentation corrections are allowed on a release branch.

Allowing new features into a release branch defeats its purpose: the release branch exists to stabilize the code before it goes to `main`. Adding new, untested code at this stage resets the stabilization clock and risks introducing regressions.

The correct course of action is to close the PR and ask the teammate to re-target it at `develop`. The async batch inference feature will ship in `2.1.0` (or `3.0.0` if it is breaking), not `2.0.0`.

</details>

### Q9 — Secret exposure

A teammate just pushed a commit that includes the following in `conf/base/parameters/model_registry.yml`:

```yaml
mlflow_tracking_uri: https://mlflow.internal.example.com
mlflow_tracking_username: admin
mlflow_tracking_password: "s3cr3tP@ssw0rd!"
```

The commit is now on `develop`. What are the exact steps to resolve this?

<details>
<summary>Answer</summary>

**Step 0 — Rotate the secret immediately.** Before doing anything with git, change the password on the MLflow server. Assume the credential is compromised the moment it was pushed, regardless of repository visibility. Git history is persistent and can be cached by mirrors, CI logs, or any developer who pulled.

**Step 1 — Remove the secret from history using `git-filter-repo`:**
```bash
pip install git-filter-repo

# Remove just the offending file, or rewrite its content
git filter-repo --path conf/base/parameters/model_registry.yml --invert-paths
```
Or if you want to keep the file but scrub the value, use `--replace-text` with a substitution file.

**Step 2 — Force push all branches:**
```bash
git push origin --force --all
git push origin --force --tags
```

**Step 3 — Notify the team.** Every developer must re-clone or hard-reset:
```bash
git fetch origin
git reset --hard origin/develop
```

**Step 4 — Prevent recurrence.**
- Move the credential to `conf/local/credentials.yml` (gitignored).
- Reference it from `parameters/` using Kedro's credential interpolation: `${credentials:mlflow_tracking_password}`.
- Enable GitHub's secret scanning and add `git-secrets` as a pre-commit hook.

Do not use `git rm` and a new commit — that only removes the file from the latest snapshot; the secret remains in history forever.

</details>

### Q10 — Tagging strategy

You have just merged `release/1.3.0` into `main`. The corresponding MLflow run ID for the model going to production is `d4e5f678`. Write the exact git commands to tag this release in a way that links the code version to the model artifact.

<details>
<summary>Answer</summary>

```bash
# Annotated tag on main with model provenance in the message
git checkout main
git tag -a v1.3.0 -m "Release v1.3.0: improved churn model. MLflow run: d4e5f678"
git push origin v1.3.0

# Optional: also tag the model artifact separately for querying by model name
git tag -a model/churn-predictor/v5 -m "Churn predictor v5: AUC 0.931 on holdout. MLflow run: d4e5f678. Released in v1.3.0"
git push origin model/churn-predictor/v5
```

Use **annotated tags** (the `-a` flag), not lightweight tags. Annotated tags are full objects in the git database with their own message, author, and timestamp — they are the right tool for release markers. Lightweight tags are just pointers with no metadata, useful only for temporary local bookmarks.

</details>

### Q12 — `git bisect`

Your model serving endpoint started returning incorrect predictions sometime between tag `v1.1.0` (known good) and the current `HEAD` on `main` (known bad). You have a Python script `tests/smoke_test.py` that exits with code 0 on correct predictions and code 1 on incorrect ones. Write the exact bisect session to identify the offending commit automatically.

<details>
<summary>Answer</summary>

```bash
git bisect start
git bisect bad                        # current HEAD is broken
git bisect good v1.1.0                # last known good tag

# Automate the bisect using the smoke test
git bisect run python tests/smoke_test.py

# Git will binary-search through commits, running the script at each step.
# When finished, it prints the first bad commit.

git bisect reset                      # return HEAD to its original position
```

`git bisect run` is the key: it accepts any command that returns exit code 0 (good) or non-zero (bad) and automates the entire binary search. For a range of 100 commits, bisect finds the culprit in at most 7 steps (log₂(100) ≈ 7).

After `git bisect reset`, inspect the identified commit:
```bash
git show <bad-commit-hash>
```

</details>

### Q13 — PR review posture

A PR adds a new `generate_drift_report` node. The reviewer leaves this comment:

> *"You forgot to handle the case where the reference dataset is empty."*

And the author replies:

> *"That can never happen in practice."*

Is the author's response appropriate? What should happen next?

<details>
<summary>Answer</summary>

The author's response is not appropriate as a final answer. "Can never happen in practice" is an assumption, not a guarantee — and in ML systems, data pipelines regularly surface unexpected edge cases (upstream schema changes, empty feature windows, first-run cold-starts).

The right responses, in order of preference:

1. **Add a guard and a test.** Handle the empty case explicitly (raise a clear `ValueError`, log a warning, return an empty report — whatever is correct for the pipeline semantics) and add a unit test for it. This is the professional response.
2. **If truly impossible, explain why and document it.** If there is a Kedro node upstream that guarantees the reference dataset is non-empty, say so, point to it, and add an assertion (`assert len(reference_df) > 0, "Reference dataset must not be empty"`) so the assumption is at least explicit and fail-fast.

The reviewer should not approve the PR until one of these two paths is taken. Approving "I'll trust you" is how silent production failures enter the system.

</details>

### Q14 — Reflog rescue

You were experimenting locally on `feature/new-architecture` and ran `git checkout develop` without committing. Git said "your changes would be overwritten" and you ran `git checkout -f develop`. Your uncommitted work is gone. Is it recoverable?

<details>
<summary>Answer</summary>

**No — not fully, and often not at all.**

`git checkout -f` discards unstaged and uncommitted changes in the working directory without creating any git object. Because the work was never staged or committed, it has no SHA-1 hash in the git object database and does not appear in the reflog.

`git reflog` only records movements of `HEAD` (commits, checkouts, resets). It cannot recover content that was never committed.

**What might partially help:**
- Your editor's local history (VS Code, PyCharm both keep undo history per file — check before closing).
- The OS temporary files or autosave (some editors write `.swp` or `~` files).
- `git fsck --lost-found` — finds dangling objects, but only if you had at least run `git add` at some point (staged changes do create blob objects).

**The real lesson:** commit early and often on local branches, even as `WIP` commits. You can always clean up with `git rebase -i` before opening a PR:
```bash
git commit -m "wip: architecture experiment checkpoint — do not merge"
# ... keep working ...
# Before PR: squash or reword wip commits
git rebase -i origin/develop
```

</details>

### Q15 — CI gating

Your `develop` branch has the following branch protection rule: "Require status checks to pass before merging" with checks `lint`, `test`, and `validate-model`. A teammate's PR has a passing `lint` and `test`, but `validate-model` is failing because the new model's AUC dropped from 0.91 to 0.87 on the validation set. The teammate argues: *"The threshold is too strict, we should just lower it."*

What is the correct response, and what should the team do?

<details>
<summary>Answer</summary>

The teammate's instinct to lower the threshold to unblock the PR is the wrong approach. The threshold exists precisely to catch this situation: a code change that degrades model performance. Lowering the threshold in response to a failing model is equivalent to disabling a smoke detector because it went off.

**Correct responses:**

1. **Investigate the regression first.** Why did AUC drop 4 points? Is it a bug in the feature engineering? A data leakage fix that accidentally removed signal? A hyperparameter that regressed? The PR should not merge until this is understood.

2. **If the drop is intentional and acceptable** (e.g., a fairness constraint was added that trades raw accuracy for bias reduction), the team should make a conscious, documented decision to update the threshold — not silently lower it to unblock a PR. Update the threshold in `conf/base/parameters/ci_cd.yml`, write a comment explaining the trade-off, and get explicit sign-off from the relevant stakeholders.

3. **If the drop is a regression**, fix the model before merging. The CI gate did exactly its job.

The broader principle: CI thresholds on model quality are the equivalent of test coverage thresholds. They exist to enforce a team contract. Bypassing them under time pressure is how model quality silently erodes over months.

</details>

```python
# src/mlops_handbook/pipelines/experiment_tracking/nodes.py
import logging
import subprocess
from typing import Any

import mlflow

logger = logging.getLogger(__name__)


def get_git_commit_hash() -> str:
    """Return the current git commit hash (short form).

    Returns:
        7-character git commit hash, or 'unknown' if git is unavailable.
    """
    try:
        return (
            subprocess.check_output(
                ["git", "rev-parse", "--short", "HEAD"],
                stderr=subprocess.DEVNULL,
            )
            .decode("utf-8")
            .strip()
        )
    except (subprocess.CalledProcessError, FileNotFoundError):
        logger.warning("Could not retrieve git commit hash.")
        return "unknown"


def log_run_metadata(
    params: dict[str, Any],
    metrics: dict[str, float],
    model_name: str,
) -> str:
    """Log parameters, metrics, and git provenance to an MLflow run.

    Args:
        params: Hyperparameters to log.
        metrics: Evaluation metrics to log.
        model_name: Name used to tag the run.

    Returns:
        The MLflow run ID.
    """
    with mlflow.start_run() as run:
        mlflow.set_tag("git_commit", get_git_commit_hash())
        mlflow.set_tag("model_name", model_name)
        mlflow.log_params(params)
        mlflow.log_metrics(metrics)
        logger.info("MLflow run %s logged successfully.", run.info.run_id)
        return run.info.run_id
```

**Step 3 — Tests:**

```python
# tests/pipelines/experiment_tracking/test_nodes.py
from unittest.mock import patch
import subprocess

from mlops_handbook.pipelines.experiment_tracking.nodes import get_git_commit_hash


def test_get_git_commit_hash_returns_seven_char_string() -> None:
    """get_git_commit_hash returns a 7-character string when git is available."""
    result = get_git_commit_hash()
    # In a real repo this will pass; in CI ensure git is available
    assert isinstance(result, str)
    assert len(result) == 7 or result == "unknown"


def test_get_git_commit_hash_returns_unknown_on_subprocess_failure() -> None:
    """get_git_commit_hash returns 'unknown' when the subprocess call fails."""
    with patch(
        "subprocess.check_output",
        side_effect=subprocess.CalledProcessError(128, "git"),
    ):
        result = get_git_commit_hash()

    assert result == "unknown"


def test_get_git_commit_hash_returns_unknown_when_git_not_found() -> None:
    """get_git_commit_hash returns 'unknown' when git binary is missing."""
    with patch(
        "subprocess.check_output",
        side_effect=FileNotFoundError,
    ):
        result = get_git_commit_hash()

    assert result == "unknown"
```

# src/mlops_handbook/pipelines/monitoring/nodes.py
import logging
import pandas as pd

logger = logging.getLogger(__name__)

REQUIRED_COLUMNS = {"prediction_score"}


def validate_monitoring_input(df: pd.DataFrame) -> pd.DataFrame:
    """Validate that the monitoring input DataFrame contains required columns.

    Args:
        df: Input DataFrame from the model output layer.

    Returns:
        The validated DataFrame, unchanged.

    Raises:
        KeyError: If any required columns are missing from the DataFrame.
    """
    missing = REQUIRED_COLUMNS - set(df.columns)
    if missing:
        raise KeyError(
            f"Monitoring pipeline received a DataFrame missing required columns: "
            f"{sorted(missing)}. Received columns: {sorted(df.columns)}"
        )
    logger.info("Monitoring input validation passed. Shape: %s", df.shape)
    return df
```

git checkout main
git merge --no-ff hotfix/fix-missing-prediction-score-keyerror -m "fix: merge hotfix for missing prediction_score KeyError"
git tag -a v1.1.1 -m "Hotfix v1.1.1: guard against missing prediction_score column in monitoring pipeline"
git push origin main --tags

# Into develop
git checkout develop
git merge --no-ff hotfix/fix-missing-prediction-score-keyerror -m "fix: back-merge hotfix for missing prediction_score KeyError into develop"
git push origin develop

git branch -d hotfix/fix-missing-prediction-score-keyerror
git push origin --delete hotfix/fix-missing-prediction-score-keyerror
```

**Step 7 — Does the hotfix need to merge into `release/1.2.0`?**

**Yes, if `release/1.2.0` is still open (not yet merged to `main`).** A release branch is a stabilization branch — it is supposed to represent production-quality code. If you know there is a bug in the monitoring pipeline and you are about to ship `1.2.0` without the fix, you are knowingly shipping a broken release.

The correct sequence:
```bash
git checkout release/1.2.0
git merge --no-ff hotfix/fix-missing-prediction-score-keyerror
```

This ensures `v1.2.0` ships with the fix already included, rather than requiring another patch release (`v1.2.1`) immediately after launch.

If `release/1.2.0` has already been merged and deleted before the hotfix was created, then merging into `develop` is sufficient — the fix will naturally be included in `v1.2.1` or `v1.3.0`.

</details>

### Task 3 — Diagnose and recover a broken `develop`

**Background:** You arrive on Monday morning to find this in `#mlops-alerts` on Slack:

> *"CI on `develop` has been red since Friday. Three PRs are blocked. Someone ran `git reset --hard` on develop and force-pushed late on Friday. One of the erased commits trained a new model — the MLflow run ID was `f9a1b2c3` but we don't know the git hash anymore."*

**Your task:**

1. Write the exact commands to find the erased commits using the reflog (assume you have a local clone that was last fetched Friday afternoon, before the reset).
2. Write the commands to restore `develop` to its correct state.
3. Explain how you would recover the git commit hash that produced MLflow run `f9a1b2c3`, assuming the team follows the `log_run_metadata` convention from Task 1.
4. Write the `.github/workflows/protect-develop.yml` GitHub Actions workflow that would have *prevented* this situation by blocking direct pushes to `develop`. The workflow should run `ruff`, `black --check`, and `pytest` on every push to `develop`, and require all three to pass before a merge is allowed.

<details>
<summary>Solution</summary>

**Step 1 — Find erased commits via reflog:**
```bash
# Your local clone still has the old refs
git reflog --all

# Look for the last known good state of develop, e.g.:
# a9f3c11 refs/remotes/origin/develop@{3}: fetch: fast-forward  ← before the reset
# 2c8d4e7 refs/remotes/origin/develop@{0}: fetch: forced-update ← the bad state

# Inspect the erased commits
git log --oneline a9f3c11
```

**Step 2 — Restore develop:**
```bash
# Reset develop to the last good commit
git checkout develop
git reset --hard a9f3c11     # the SHA before the bad force push

# Force push with the safety lease
git push --force-with-lease origin develop

# Alert the team to hard-reset their local develop
# git fetch origin && git reset --hard origin/develop
```

**Step 3 — Recover the git hash from MLflow:**

Because `log_run_metadata` sets the tag `git_commit` on every run, the hash is stored directly in MLflow:

```python
import mlflow

client = mlflow.MlflowClient()
run = client.get_run("f9a1b2c3")
git_hash = run.data.tags.get("git_commit")
print(git_hash)  # e.g. "a3f8c12"

# Inspect the commit
# $ git show a3f8c12
```

This is exactly why logging the git hash to every MLflow run is non-negotiable: it transforms this crisis from "we have no idea what code trained this model" into a two-line recovery.

**Step 4 — GitHub Actions workflow:**

```yaml
# .github/workflows/protect-develop.yml
name: Protect develop

on:
  push:
    branches:
      - develop
  pull_request:
    branches:
      - develop

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.10"

      - name: Install dependencies
        run: pip install ruff black

      - name: Run ruff
        run: ruff check src/ tests/

      - name: Run black (check only)
        run: black --check src/ tests/

  test:
    name: Test
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.10"

      - name: Install project
        run: pip install -e ".[dev]"

      - name: Run pytest
        run: pytest tests/ -v --tb=short
```

For this workflow to **block merges** (not just report), you must also configure the branch protection rule in GitHub:

```
Settings → Branches → Branch protection rules → develop
☑ Require status checks to pass before merging
  Status checks required: Lint, Test
☑ Require branches to be up to date before merging
☑ Do not allow bypassing the above settings
```

The combination of the workflow (which defines the check names) and the branch protection rule (which enforces them as gates) is what prevents the force-push scenario: even if someone resets `develop` locally, they cannot push without CI passing — and CI cannot pass on a branch that has diverged from a known-good state without review.

</details>
