## Part 1 — Conceptual Quiz

Answer each question in 2–4 sentences. Vague answers ("MLflow tracks things") will not demonstrate understanding.

---

**Q1.** A colleague argues that logging metrics to a shared spreadsheet is equivalent to MLflow tracking because "the data ends up in the same place." Give two concrete reasons why this comparison breaks down in a production ML team.

<details>
<summary>Answer</summary>

Two reasons the spreadsheet analogy breaks down:
 
First, a spreadsheet has no enforced schema. Columns drift: one run logs `lr`, another logs `learning_rate`, a third forgets it entirely. MLflow enforces a consistent key-value structure per run and makes params and metrics queryable programmatically via `client.search_runs()`. You cannot reliably filter 200 spreadsheet rows by metric threshold and sort by F1 in a CI script.
 
Second, a spreadsheet has no artifact linkage. A run's metrics are meaningless without the model file, the preprocessor, and the dataset version that produced them. MLflow stores artifacts alongside the run metadata and links them by `run_id`. A spreadsheet row has no equivalent: you end up with a metrics table that points nowhere, and the model file sitting in an `outputs/` folder with no traceable connection to the numbers you logged.

</details>

**Q2.** You have a training run where `mlflow.log_metric("val_f1", score)` is called once per epoch inside a loop, but you forgot to pass `step=epoch`. The run completes without errors. What is actually stored in MLflow, and what is lost?

<details>
<summary>Answer</summary>

By logging the metric at each epoch without passsing the `step=epoch` parameter erases the metric at each epoch. At the end of the run, only the last value of the metric will be kept, loosing the evolution of the metric over the epochs.

</details>

**Q3.** Explain the difference between a **parameter** and a **metric** in MLflow's data model. Give one example of each from the `train_classifier` node in `1.1_how_to_track_your_model.md` and explain why it belongs in that category and not the other.

<details>
<summary>Answer</summary>

A **parameter** is a value you set before training that controls the learning process. It is logged once and does not change during a run. A **metric** is a value you measure as a result of training — it reflects model behaviour on data and may change over time (per epoch or per evaluation).
 
From `train_classifier`: `n_estimators=200` is a parameter — it is an input to the `RandomForestClassifier` constructor, chosen before any data is seen, and fixed for the duration of the run. It cannot be a metric because it is not measured, it is decided. `val_roc_auc` is a metric — it is computed from the model's predictions on the held-out validation set after training completes. It cannot be a parameter because it is an output, not an input; you do not set it, you observe it.

</details>

**Q4.** The guide states: *"Log params before calling `fit()`. If your training crashes mid-run, you want the params that caused the crash recorded."* A teammate disagrees: "If the run crashes, it's incomplete anyway — why does it matter what's logged?" Write the counter-argument.

<details>
<summary>Answer</summary>

It matters to log the parameters that caused the crash in order to avoid to retrain a model with the same parameters to avoid another crash. Plus, it helps to select the right model if one crashes with a specific range of paramters - one behaviour you might want to avoid in production.

</details>

**Q5.** `mlflow.autolog()` is called at the top of a training script that is run weekly in a GitHub Actions workflow. The team upgrades scikit-learn from 1.3 to 1.5. Name two specific failure modes that could silently degrade the quality of your run history after the upgrade.

<details>
<summary>Answer</summary>
 
Two silent failure modes after a scikit-learn upgrade with `mlflow.autolog()`:
 
1. **Param names change or disappear.** scikit-learn occasionally renames, deprecates, or restructures constructor parameters between minor versions. If `autolog` captures param names directly from the estimator's `get_params()`, a renamed parameter (e.g., `n_iter_no_change` becoming something else) will appear under a different key in runs after the upgrade. Older runs use the old key, newer runs use the new key. Any dashboard, search filter, or promotion script that queries by param name now silently misses half the runs — no error, just wrong results.
2. **New metrics are added or existing metrics are renamed.** Autologging captures whatever metrics the integration exposes for that framework version. A new scikit-learn version may add metrics that weren't logged before (changing the schema of your run history) or rename existing ones. A `search_runs` filter like `metrics.training_score > 0.9` may stop matching any runs after the upgrade if the metric was renamed, again with no error — it simply returns an empty result set.

</details>

### Task 1 — Fix a Broken Tracking Node

The following node was written by a junior data scientist and contains **four distinct tracking mistakes**. Identify each one, explain why it is a problem, and rewrite the function correctly.

The function lives at `src/mlops_handbook/pipelines/experiment_tracking/nodes.py` and is called by a Kedro pipeline. Parameters come from `conf/base/parameters/experiment_tracking.yml`.

```python
import mlflow
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import f1_score
from sklearn.model_selection import train_test_split


TRACKING_URI = "http://10.0.1.55:5000"


def train_gbm(features, target, params):
    mlflow.set_tracking_uri(TRACKING_URI)
    mlflow.set_experiment("models")

    X_train, X_val, y_train, y_val = train_test_split(
        features, target, test_size=0.2, random_state=42
    )

    run = mlflow.start_run()

    model = GradientBoostingClassifier(
        n_estimators=params["n_estimators"],
        learning_rate=params["learning_rate"],
    )
    model.fit(X_train, y_train)

    mlflow.log_params({
        "n_estimators": params["n_estimators"],
        "learning_rate": params["learning_rate"],
        "test_size": 0.2,
        "random_state": 42,
    })

    val_f1 = f1_score(y_val, model.predict(X_val))
    mlflow.log_metric("f1", val_f1)

    mlflow.end_run()

    return model
```

Your answer must: name all four mistakes, explain the consequence of each, and provide a corrected version of the function.

<details>
<summary>Answer</summary>


**Mistake 1: Hardcoded tracking URI**
```python
TRACKING_URI = "http://10.0.1.55:5000"
mlflow.set_tracking_uri(TRACKING_URI)
```
A hardcoded IP address breaks for every developer not on that specific network, and fails silently in CI where the server is unreachable — the run either errors or falls back to local `mlruns/` without warning. The tracking URI must come from the environment variable `MLFLOW_TRACKING_URI`, keeping it out of source code entirely.
 
**Mistake 2: Non-descriptive experiment name**
```python
mlflow.set_experiment("models")
```
`"models"` is meaningless at scale. Every pipeline in the project would dump runs into the same experiment, making the UI and `search_runs()` queries useless. Experiment names must identify the modelling task: `"churn_prediction"`, `"fraud_detection"`, etc.
 
**Mistake 3: `start_run()` used without a context manager**
```python
run = mlflow.start_run()
# ...
mlflow.end_run()
```
If any line between `start_run()` and `end_run()` raises an exception, `end_run()` is never called. The run stays in `RUNNING` state indefinitely in the tracking server and is excluded from `search_runs()` results by default. The `with mlflow.start_run():` context manager guarantees cleanup on both success and failure.
 
**Mistake 4: Params logged after `fit()`**
```python
model.fit(X_train, y_train)
mlflow.log_params({...})
```
If `fit()` raises an exception (OOM, numerical instability, etc.), the run ends with no params recorded. The crashed run is then indistinguishable from a run that never started, losing the only diagnostic information available. Params must be logged before training begins.

</details>

### Task 2 — Extend the Pipeline for Epoch-Level Logging

The `train_classifier` node in `01_mlflow.md` trains a `RandomForestClassifier`, which has no meaningful epoch loop. You are now replacing it with a `GradientBoostingClassifier`, which supports staged prediction via `staged_predict()` — allowing you to evaluate performance after each tree is added.

**Your task:**

1. Add a `log_staged_metrics` helper function to `src/mlops_handbook/pipelines/experiment_tracking/nodes.py` that accepts a fitted `GradientBoostingClassifier`, validation data, and an open MLflow run, and logs `val_f1` and `val_roc_auc` at each stage (tree) using the correct `step` argument.

2. Update `conf/base/parameters/experiment_tracking.yml` to add any new parameters your implementation requires.

3. In 3–4 sentences, explain why step-aware metric logging matters when you later use `client.search_runs()` to automate model promotion — what information would be missing if you only logged the final metric?

Your implementation must use type hints and Google-style docstrings, consistent with the project conventions in the system prompt.

<details>
<summary>Answer</summary>

**1. `log_staged_metrics` implementation:**
 
```python
# src/mlops_handbook/pipelines/experiment_tracking/nodes.py
 
import logging
from typing import Any
 
import mlflow
import numpy as np
import pandas as pd
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import f1_score, roc_auc_score
 
logger = logging.getLogger(__name__)
 
 
def log_staged_metrics(
    model: GradientBoostingClassifier,
    X_val: pd.DataFrame,
    y_val: pd.Series,
) -> None:
    """Log per-stage val_f1 and val_roc_auc for a fitted GradientBoostingClassifier.
 
    Iterates over staged predictions to record metric values after each tree
    is added. Requires an active MLflow run in the calling context.
 
    Args:
        model: A fitted GradientBoostingClassifier.
        X_val: Validation feature matrix.
        y_val: Validation target vector.
    """
    staged_proba = model.staged_predict_proba(X_val)
    staged_pred = model.staged_predict(X_val)
 
    for step, (proba, pred) in enumerate(zip(staged_proba, staged_pred)):
        val_f1 = f1_score(y_val, pred)
        val_roc_auc = roc_auc_score(y_val, proba[:, 1])
 
        mlflow.log_metric("val_f1", val_f1, step=step)
        mlflow.log_metric("val_roc_auc", val_roc_auc, step=step)
 
    logger.info(
        "Logged staged metrics for %d estimators. "
        "Final val_f1=%.4f, val_roc_auc=%.4f",
        step + 1,
        val_f1,
        val_roc_auc,
    )
```
 
This function is called inside an active `with mlflow.start_run():` block in the parent training node — it does not open its own run.
 
**2. Updated parameters file:**
 
```yaml
# conf/base/parameters/experiment_tracking.yml
 
n_estimators: 200
learning_rate: 0.05
random_state: 42
test_size: 0.2
```
 
`learning_rate` replaces `max_depth` from the `RandomForestClassifier` example. `n_estimators` now also controls the number of stages logged, so its value directly determines how many metric points appear in the UI per run.
 
**3. Why step-aware logging matters for automated promotion:**
 
`client.search_runs()` filters and ranks runs by their logged metric values. When only the final metric is logged, every run appears as a single point — you can compare final F1 scores, but you cannot distinguish a model that converged cleanly at stage 80 from one that overfit badly after stage 120 and happened to recover. Step-aware logging exposes the full learning curve, which means a promotion script can apply richer criteria: for example, requiring that `val_roc_auc` at stage 50 already exceeds a minimum threshold (early stability check), not just that the final value does. Without per-step data, automated promotion is blind to training dynamics and can pass a model that got lucky on the final evaluation but is fundamentally unstable.

</details>
